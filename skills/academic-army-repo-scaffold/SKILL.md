# Academic Army Repo Scaffold

## Purpose

Initialize a real research-code starter repository, then add the Academic Army
experiment scaffold. The primary artifact is the generated starter repo plus
fixed experiment overlay. `README.md`, `README.zh-CN.md`, `REFERENCES.md`, and
`REFERENCES.zh-CN.md` are supporting documentation, not the scaffold itself.

This skill is scaffold-only. Do not implement the paper method, experiment
workflow, data loaders, metrics, result exporters, harness logic, test logic,
configuration parsing, or experiment runners. You may invoke an initializer,
template tool, official starter command, or template repository to generate
starter files, boilerplate source, package metadata, build/test configuration,
minimal entry files, and ecosystem conventions. Do not install project
dependencies, run generated code, run tests, run harnesses, or execute
experiments.

Interpret scaffold-only narrowly: no paper business implementation. Do not
interpret it as no starter source, no package metadata, no build config, or no
template boilerplate. Those starter files are the core scaffold product.

If the final repository would contain only Markdown files, empty directories,
and placeholder notes, stop and report that scaffold generation failed. A
documentation-only artifact is not a completed repository scaffold.

Anti-regression gates from prior artifacts:

- Missing `README.md` `## Installation` or `README.zh-CN.md` `## 安装` is an
  immediate validation failure.
- Empty dependency declarations are allowed only when README, REFERENCES, and
  any manifest explicitly say "none selected at scaffold stage" and explain
  why no installable dependencies were declared.
- A fixed top-level test directory is a failure unless the selected template or
  DeepResearch evidence specifically justifies that singular path. Prefer the
  generated test structure; when none is generated, document the researched
  ecosystem convention before creating any test placeholder path.
- `REFERENCES.md` must be category-driven, not narrative-only. It must include
  installable-dependency, reference-only, harness/benchmark, installation, and
  rejected-candidate classifications.
- `SCAFFOLD_MANIFEST.md`, if written, is a validation report. It must not mark
  validation as passed unless installation sections, dependency/reference
  consistency, test-layout provenance, and scaffold-only boundaries were
  actually checked.
- `REFERENCES.zh-CN.md` must read as Chinese documentation with translated
  field labels and explanations. English keys such as `name`, `url`,
  `used_for`, or `reuse_decision` should not appear as the primary field
  labels in the Chinese file.

## Required Inputs

Require a user-specified target repository path. If the path is missing, ask
for it before creating files.

Read only the inputs needed to scaffold the repository:

- `paper_blueprint`
- experiment plan
- coding plan
- explicit user constraints about language, framework, template, repository
  path, or existing repository adaptation

If explicit planning paths are provided, read those files. Otherwise locate the
closest conventional planning artifacts by name, then stop. Do not explore
unrelated nearby files, logs, source trees, notebooks, dependency manifests, or
old outputs merely because they are present.

Read files inside the target repository only when the user explicitly asks to
initialize or adapt an existing repository, when an initializer generated files
there that must be inspected, or when an existing scaffold file must be
preserved.

## Path And Preservation Rules

Keep every created or modified file under the target repository path. Resolve
the target path before writing and reject any path that escapes it.

Inside repository documents:

- Use repository-relative paths for files inside the generated repository.
- For planning inputs outside the repository, label them as external task
  inputs. Prefer the user-supplied workspace-relative convention, or a stable
  relative path from the repository root such as `../paper_blueprint.md` only
  when it truly resolves outside the repository. Avoid hardcoded machine
  absolute paths unless the user supplied only absolute paths and no portable
  convention exists.
- Use the same external-input path convention in README, REFERENCES, and any
  manifest.

If the target path already contains files, classify them before changing
anything:

- existing starter-repo files to preserve
- generated placeholder docs that can be refreshed safely
- generated scaffold residue that can be pruned safely
- user-authored or ambiguous content that must be preserved

Create missing scaffold files and folders. Do not overwrite non-placeholder
content. Ask before destructive replacement when authorship is unclear.
If the existing target is a previous Markdown-only or documentation-only
scaffold, do not accept it as initialized. Upgrade it by generating or merging
a real starter repository layer, while preserving any user-authored content.

Keep runtime mechanics out of generated repository documents. Do not write
about sandbox limits, shell failures, MCP failures, dependency-install
failures, or local workaround details unless the user explicitly asks for
operational notes outside the scaffold.

## Required DeepResearch

Run `academic_army_mcp_tools.deepresearch` before choosing the initializer or
template, unless the current task includes a fresh, directly relevant lookup
artifact that already compares scaffold-generation options.

DeepResearch must focus on ways to actually generate starter repository
structure for the target ecosystem:

- official initialization commands
- template tools such as Cookiecutter, Copier, Yeoman, framework CLIs, or
  ecosystem package generators
- high-quality template repositories or GitHub template repositories
- research-code templates, benchmark templates, and harness templates
- high-quality public repositories in the paper domain, used for structure
  lessons or later implementation references
- ecosystem package-management and dependency-declaration conventions
- repo-local, workspace-local, environment-isolated, sandboxed, or containerized
  installation practices
- ecosystem test-layout conventions and test discovery behavior when the
  selected initializer does not generate tests

Do not hardcode a tool, language, package manager, test framework, config file,
or source layout in the skill. Select at invocation time based on the planning
inputs, explicit user constraints, template quality, license clarity,
maintenance, generated output shape, and downstream implementation cost.

When no language/runtime is specified, infer a practical starter ecosystem from
the plans and DeepResearch evidence. For research systems with simulation,
metrics, trace processing, and CAGS/PyTorch/CUDA adapter boundaries, a Python
research-code starter is often plausible, but still justify the choice from the
task evidence. Leaving language/runtime undecided is a validation failure
unless adapting an existing repository that already has a clear starter
ecosystem.

Use a prompt like:

```text
Research template-first repository initialization options for an Academic Army
research-code project.

Project context:
[paper goal, field, candidate methods, experiment plan harness needs, coding
plan logical modules, explicit language/framework/template preferences, target
repository constraints]

Return scaffold-generation evidence:
- official initializers, template tools, template repositories, research-code
  templates, benchmark templates, and related high-quality repositories
- expected generated output shape for each candidate: source layout,
  dependency declaration, build/test configuration roles, entry points, docs,
  examples
- generated or conventional test structure, and how coding-plan test categories
  should be mapped into that structure without fighting the ecosystem
- dependency declaration mechanism, environment isolation approach, and
  repo-local installation workflow used by the target ecosystem
- installable dependency candidates versus reference-only sources, including
  license, packaging quality, interface stability, maintenance, and risk notes
- license, exact release tag, package version, commit SHA, or dated unpinned
  access snapshot
- maintenance and complexity notes
- which candidates are safe to generate from, adapt, cite only, or reject
- recommended initializer/template for this project and why
```

If multiple candidates remain plausible, compare their generated output shape
before choosing. It is acceptable to inspect documentation, run a dry generator
in a disposable location, or clone a template for static inspection. Do not
evaluate candidates by descriptions alone when generated structure is unclear.
Record the comparison at the level of generated files and directories, not only
feature descriptions.

DeepResearch should classify external sources into two groups:

- **Installable dependencies:** packaging is clear, license is compatible or
  acceptable for the project, interfaces are stable enough, and the source is
  suitable to declare in the target ecosystem's dependency manifest.
- **Reference-only sources:** useful for later implementation, benchmark
  structure, harness ideas, or domain understanding, but unsuitable to install
  directly because of license uncertainty, heavy or unstable dependencies,
  unclear packaging, maintenance risk, incompatible scope, or because only a
  small idea rather than a reusable library is needed.

Do not install, resolve, lock, download, or import project dependencies during
this skill. Only declare selected installable dependencies in the generated
project's dependency configuration. If no installable dependencies are selected
at scaffold stage, record that explicit decision in README, REFERENCES, and
the manifest, and leave the dependency manifest empty or template-default.

## Template-First Scaffold Design

Use a hybrid layout:

- **Template layer:** generated by the selected initializer, template tool,
  official starter, or template repository. This layer should provide real
  starter-repo structure such as project metadata, dependency declarations,
  source layout, build/test configuration roles, minimal entry points, examples,
  or ecosystem-specific artifacts discovered from the selected template.
- **Experiment overlay:** fixed Academic Army directories and documentation
  required for every scaffold.

Always create or preserve these top-level overlay entries:

- `data/`: input data and future dataset assets
- `output/`: program run outputs and intermediate artifacts
- `results/`: experiment result records and paper-facing summaries
- `harness/`: all research/evaluation harnesses
- `README.md`: English repository overview
- `README.zh-CN.md`: Chinese repository overview
- `REFERENCES.md`: English provenance and external references
- `REFERENCES.zh-CN.md`: Chinese provenance and external references

The fixed directories define top-level experiment workflow semantics only. They
do not prescribe the language ecosystem's internal source or test layout.
Preserve the starter repo's source directories, package metadata, dependency
declarations, test structure, build configuration, minimal entry files, and
ecosystem conventions unless they are unrelated sample-app residue or ambiguous
third-party code with unsuitable licensing.

Distinguish template starter code from paper business code:

- Starter boilerplate generated by the selected template may remain.
- Minimal template entry files may remain if they are part of normal ecosystem
  scaffolding.
- Paper-specific scheduling, CAGS integration, metrics, data loading, result
  export, harness execution, and test logic must not be implemented.

Empty marker files may be useful, but they do not by themselves prove starter
generation. A new scaffold needs at least one substantive artifact discovered
from the selected template, such as project metadata, dependency declaration,
build configuration, generated source/package layout, or an initializer-specific
project artifact. Do not name or validate ecosystem-specific files in this
skill.

If a template generates directories whose names overlap the fixed overlay
semantics, keep the fixed top-level Academic Army convention and explain the
relationship in the README. Do not let template directories replace
`data/`, `output/`, `results/`, or `harness/`.

Testing is template-informed, not a fixed overlay. First inspect the selected
initializer's generated test structure. If it exists, map the coding-plan test
categories into that structure with semantic subfolders or explanation files.
If the initializer does not generate tests, use DeepResearch evidence for the
target ecosystem's conventional test layout and create the smallest compatible
test structure inside that ecosystem convention. Do not create a fixed top-level
test directory unless the template or DeepResearch-supported ecosystem
convention justifies it. If both a template test structure and an extra test
directory would exist, validate and document why both are needed; otherwise use
the template structure.

Record the test-layout decision in README, REFERENCES, and any manifest:

- whether the initializer generated test files or directories
- exact generated test paths retained
- how each coding-plan test category maps into those paths
- if no tests were generated, which DeepResearch sources justify the chosen
  path and why a fixed top-level test directory was not imposed

Create additional source/package placeholder directories conservatively. The
template-generated source layout is the source of truth. Add source namespace
placeholders only when they are directly implied by the coding plan's logical
modules or by the selected template's conventions, and document that they are
manual scaffold reservations rather than finalized architecture. Avoid filling
the template-selected source layout with many empty directories merely to mirror
every planning noun. If the relationship between top-level `harness/` and future
executable harness code is represented in source placeholders, use an
unambiguous template-appropriate runner/module location and explain the
distinction in README.

If a template generates sample boilerplate, either preserve it as clearly
identified template starter code or remove it with a documented scaffold-level
reason. Do not let sample starter code appear to be a paper method, harness,
metric, loader, or runner.

## Project Artifact Registry

After selecting the template and generating the repository, build an internal
`project artifact registry`. It should be the single source of truth for
generated documentation and validation. Record discovered artifacts by role, not
by predeclared file name:

- target repository root
- external planning inputs and path convention
- inferred language/runtime and rationale
- selected initializer/template/tool/repository
- generation command or generation method
- template source URL, license, version/package version/commit/access snapshot
- generated starter files retained
- generated files removed or adjusted, with scaffold-level reason
- candidate templates considered and rejected reasons
- generated or DeepResearch-supported test layout, and how each coding-plan
  test category maps into it
- project metadata artifacts discovered from the template
- dependency declaration artifacts discovered from the template or target
  ecosystem
- build, run, package, and tool configuration artifacts discovered from the
  template
- source layout selected by the template
- test layout selected by the template or DeepResearch
- selected installable dependencies, or the explicit decision that none are
  selected at scaffold stage
- reference-only sources and why they were not declared as dependencies
- repo-local or environment-isolated installation strategy
- fixed overlay directories
- harness names, purposes, metrics, inputs, and artifacts
- test category names, fixtures, pass/fail meaning, and protected areas
- current scaffold tree
- static validation checklist and next implementation handoff

Do not include sandbox notes, tool failure logs, dependency-install problems,
or local workaround details in the manifest or generated repo docs.
The project artifact registry is an internal work list. It does not need to be
written as a separate file. If a manifest is written as a separate file, make it
a rigorous validation/provenance report rather than a loose duplicate of README
and REFERENCES. It must check the hardest requirements: template generation,
dependency/reference consistency, repo-local installation documentation,
test-layout provenance, fixed overlay directories, harness/test placeholder
coverage, and scaffold-only boundaries.

Do not mark validation items as passed until the corresponding static checks
have actually been performed. A manifest that repeats the intended design
without checking installation sections, dependency/reference consistency,
installable-vs-reference-only classification, and test-layout provenance is a
validation failure. If these checks cannot be completed, do not present the
manifest as passed.

Do not name or validate any ecosystem-specific files or directories in this
skill. Identify dependency declarations, build configuration, source layout, and
test layout from the selected template and generated repository, then validate
those discovered artifacts by role.

The manifest, if created, should be short enough to audit and strict enough to
fail the artifact. Avoid duplicating long README/REFERENCES prose; put
validation status, discovered artifact roles, actual dependency state, and
actual scaffold-only checks there.

## Harness And Test Placeholders

Derive harness categories from the experiment plan and coding plan. Create one
semantic subfolder under `harness/` for each harness. Use readable names such
as `candidate-method-selection`, `full-system-deadline-qoe`, or
`coupled-stress-robustness`, not abstract labels such as `c1`, `c2`, or `h3`.

Each harness subfolder must contain a short explanation file, normally
`README.md`, describing:

- harness purpose
- associated experiment goal or paper claim
- future entrypoint that should be implemented later
- expected inputs
- expected metrics
- expected output artifacts
- implementation placeholder and ownership boundary

Derive test categories from the coding plan's testing structure. Map each
category into the generated template's test structure. If no test structure was
generated, create one using DeepResearch-supported ecosystem convention, such
as the conventional test layout, package-local test area, workspace test module,
framework-specific test area, or equivalent for the selected runtime.
Use semantic names such as `data-loading`, `metric-computation`,
`result-export`, or `cli-smoke`, adapted to the ecosystem's naming convention.
Do not hardcode any test directory name in the skill.

Each test subfolder must contain a short explanation file describing:

- functional behavior to validate
- future fixtures or toy inputs
- expected outputs or exceptions
- pass/fail meaning
- harness or implementation area protected by the tests
- implementation placeholder and ownership boundary

Harness/test notes reserve structure only. They must not contain working
harness logic, test code, fixture data, or claims that validation is already
implemented.

Keep top-level `harness/` semantically separate from source code. Top-level
`harness/` is for paper-goal harness descriptions and future experiment
workflow ownership. Any package/module path reserved for executable harness
code must be named and described as future implementation code, not as a second
copy of the harness documentation tree.

If the template already generated a sample test file, preserve it when it is
normal starter boilerplate and license-compatible. Do not convert it into a
paper-specific test. If it conflicts with scaffold-only boundaries or unclear
third-party licensing, remove or adjust it only with a documented
scaffold-level reason.

## Dependency And Installation Contract

Use DeepResearch and the generated template to determine the dependency
declaration mechanism. Describe these artifacts by role, such as dependency
declaration, project metadata, workspace metadata, environment declaration, or
framework-specific dependency declaration. Do not hardcode ecosystem-specific
file names into the skill.

For each candidate external library or tool:

- classify it as an installable dependency, reference-only source, rejected
  candidate, or future implementation reference
- record license, version or recommended version range, packaging quality,
  interface stability, maintenance state, and direct-use risk
- declare installable dependencies in the template's native dependency
  mechanism only when they are appropriate for direct import/use by future code
- keep reference-only sources out of dependency manifests and record them in
  REFERENCES instead

It is valid for a scaffold to select no installable runtime dependencies when
the coding plan is not ready to commit to APIs. In that case:

- leave the dependency declaration empty or template-default
- state "none selected at scaffold stage" in README, README.zh-CN,
  REFERENCES, REFERENCES.zh-CN, and any manifest; Chinese docs may translate
  the phrase but must preserve the same decision
- explain that reference-only sources were recorded for later implementation
  and were not added to project dependencies
- ensure the dependency manifest, installation instructions, and REFERENCES
  agree exactly about the empty or template-default dependency state

Do not run install commands, dependency resolution, lockfile generation, tests,
harnesses, or generated code. If the template generated a lockfile before this
skill touched the project, preserve it when appropriate; otherwise do not create
a new lockfile that requires dependency resolution.

README installation instructions must separate:

- **System prerequisites:** global tools the user must already have, such as
  the selected ecosystem's package manager or compiler toolchain.
- **Project dependencies:** dependencies declared and managed by this
  repository.

Installation instructions must prefer repo-local, project-local,
workspace-local, environment-isolated, sandboxed, or containerized setup
supported by the selected ecosystem. They must not instruct users to install
project dependencies into a global environment by default. They must also state
that this scaffold declares dependencies and installation steps only; the skill
does not run installation.

## README Contract

Create both `README.md` and `README.zh-CN.md`.

Both READMEs must describe the actual generated scaffold and cover:

- project purpose and external planning inputs
- inferred language/runtime and why it was selected
- selected initializer/template, generation method, and template source
- starter-repo structure generated by the template layer
- installable dependency decision and the dependency declaration mechanism
- repo-local or environment-isolated installation instructions
- fixed experiment directories and their intended use
- reserved harness locations
- generated or researched test structure, and where each test category is
  reserved inside that structure
- distinction between top-level `harness/` for paper evaluation scaffolding and
  any package/module namespace reserved for future harness implementation
- what later implementation skills should fill in
- scaffold-only boundary

`README.md` must contain an `Installation` section. `README.zh-CN.md` must
contain a corresponding `安装` section. These sections must:

- tell the user to work from the repository root
- list required system prerequisites without claiming the skill installed them
- use the selected ecosystem's repo-local, project-local,
  environment-isolated, sandboxed, or container workflow when available
- explain how project dependencies declared by the scaffold should be installed
  later without polluting the global environment
- state whether installable dependencies were selected or none were selected at
  scaffold stage
- state that this skill did not run installation, dependency resolution, tests,
  harnesses, or experiments
- avoid commands that run paper methods, tests, harnesses, or experiments

Use exact Markdown headings unless a target ecosystem has a compelling reason
not to:

- `## Installation` in `README.md`
- `## 安装` in `README.zh-CN.md`

Validation should search for these actual headings, not just the words
"Installation" or "安装" somewhere in prose.

The English and Chinese READMEs need not be literal translations, but they must
agree on the template source, generated structure, input path convention,
harness list, test mapping, dependency decision, installation strategy, and
handoff point.

Do not claim that the paper method, experiment pipeline, harnesses, tests,
metrics, loaders, exporters, or runners already work.

## REFERENCES Contract

Create both `REFERENCES.md` and `REFERENCES.zh-CN.md`.

They must record DeepResearch provenance and the final template-generation
decision. Use these exact top-level sections in title case unless a target
ecosystem has a strong reason to rename one; if renamed, the manifest must map
the local name back to this contract:

- `Selected Template`
- `Installation Strategy`
- `Installable Dependencies`
- `Reference-Only Sources`
- `Harness References`
- `Benchmark References`
- `Future Implementation References`
- `Rejected Candidates`

Do not replace this schema with narrative headings such as `Selected Generator`,
`Build Backend`, or `Rejected Or Consulted Scaffold Candidates` unless those
headings are nested under the required categories. `Selected Template` is the
template-source category; `Installation Strategy` is the package-management and
repo-local setup category; `Installable Dependencies` must exist even when it
contains only the explicit none-selected decision.

If no installable dependencies are selected, the `Installable Dependencies`
section must explicitly say that none were selected at scaffold stage and why.

Each source entry should use explicit fields:

- `name`
- `url`
- `license`
- `version_or_commit`: release tag, package version, commit SHA, documentation
  version, or dated unpinned access snapshot
- `access_date`
- `used_for`: final template source, generation tool, structure pattern,
  harness organization, benchmark organization, test organization, package
  management, repo-local installation, installable dependency, reference-only
  source, rejected candidate, or later implementation reference
- `selection_reason`
- `reuse_decision`: generated-from, retained, adjusted, installable-dependency,
  consulted, cited-only, rejected, reference-only, or future implementation
  reference
- `copied_or_generated_files`: exact retained/generated files or `none`

Prefer exact pins. If a source cannot be pinned, record it as a dated unpinned
snapshot and state why. Do not use vague phrases such as "latest
documentation", "current documentation", branch visibility, or commit counts
as substitutes for exact pins or dated snapshots.

For the selected template or initializer, REFERENCES must state:

- generation command or method used
- license and version/commit/source snapshot
- which generated starter files were retained
- which generated files were removed or adjusted
- why this option was selected over rejected candidates
- how its dependency declaration mechanism is used
- whether it generated a test structure; if not, which DeepResearch-supported
  ecosystem convention is used for test placeholders

For each installable dependency, REFERENCES must state:

- project name and source URL
- license
- version, recommended version range, or dated dependency decision
- intended future module, harness, or scaffold purpose
- why it is suitable for direct installation/use
- where it was written in the project's dependency declaration

For each reference-only source, REFERENCES must state:

- project name and source URL
- license status, including unknown or incompatible license warnings
- reference value for later implementation
- why it was not declared as a dependency
- explicit instruction not to copy or directly reuse code when license or
  compatibility is unclear

If DeepResearch finds useful external implementation code, cite it as a
reference-only or future implementation reference. Do not copy or port
implementation code during this scaffold stage.

Use `consulted` for sources used only for ideas or vocabulary. Use
`generated-from`, `retained`, or `adjusted` only when the source actually
produced files in the repository or a generated file was scaffold-level
modified.

`REFERENCES.zh-CN.md` does not need to be a literal translation, but it must
cover the same decisions in Chinese: selected template, installable dependency
classification, reference-only sources, test layout provenance, installation
strategy, retained/adjusted template files, rejected candidates, and future
implementation references.

The Chinese REFERENCES should be readable Chinese documentation, not an English
field dump. Translate section headings and field labels such as name, license,
access date, used for, selection reason, reuse decision, and generated files
into Chinese. Keep code identifiers, package names, URLs, license identifiers,
version strings, and canonical reuse-decision values in their original form
when translation would reduce precision, but explain their meaning in Chinese.

For Chinese source entries, prefer labels such as `名称`, `链接`, `许可证`,
`版本或提交`, `访问日期`, `用途`, `选择理由`, `复用决定`, and
`复制或生成的文件`. Avoid leading every entry with English labels such as
`name`, `url`, `license`, `used_for`, or `copied_or_generated_files`.

## Workflow

1. Resolve the target repository path and confirm it is the only write scope.
2. Read the paper blueprint, experiment plan, coding plan, and explicit user
   constraints only.
3. Extract scaffold requirements: ecosystem signals, expected implementation
   direction, experiment types, harness categories, test categories, input data
   expectations, and output/result artifact families.
4. Run DeepResearch for official initializers, template tools, template
   repositories, research-code templates, benchmark templates, related repos,
   generated output shapes, package management, repo-local installation, test
   layout conventions, installable dependency candidates, and reference-only
   sources.
5. Infer and record the language/runtime. Do not leave it undecided when
   creating a new scaffold.
6. Compare candidate generated structures and choose an initializer/template.
7. Generate the base starter repository inside the target path. If the target
   already contains generated documentation-only scaffold residue, generate in
   a disposable location and merge the starter files into the target rather
   than overwriting ambiguous content.
8. Preserve template-generated starter structure and remove only unrelated
   sample-app residue, unsuitable third-party code, or files that conflict with
   the scaffold boundary.
9. Inspect the generated dependency declaration mechanism and test structure.
10. Classify external libraries as installable dependencies or reference-only
   sources. Write selected installable dependencies into the template's native
   dependency declaration. If none are selected, record that explicit decision
   and keep the declaration empty or template-default.
11. Determine the repo-local or environment-isolated installation strategy from
   the template and DeepResearch evidence.
12. Overlay fixed directories: `data/`, `output/`, `results/`, and `harness/`.
13. Add semantic harness placeholder folders under `harness/` with explanation
   files.
14. Map coding-plan test categories into the generated or DeepResearch-backed
   ecosystem test structure and add explanation files there.
15. Create `README.md`, `README.zh-CN.md`, `REFERENCES.md`, and
   `REFERENCES.zh-CN.md` from the manifest, including installation,
   dependency, reference-only, and test-layout provenance.
16. Run static scaffold validation. If starter generation did not occur or the
   project artifact registry cannot identify substantive template-derived
   project artifacts, fail the task instead of delivering a Markdown-only
   repository.

The final validation step is a hard gate. If any required installation section,
dependency decision, REFERENCES category, test-layout provenance statement, or
scaffold-only boundary check is missing or inconsistent, revise the scaffold
before final response. Do not rely on prose intent; check the actual generated
files.

If static validation fails, do not summarize the artifact as complete. Revise
the scaffold and re-run the static checks. Only report success after the
validation gates pass.

## Static Validation

Perform static checks only. Do not install dependencies, lint, format, type
check, run generated project code, run generated project scripts, run tests,
run harnesses, or execute experiments.

Validation must confirm:

- every created or modified path is inside the target repository
- a starter repo was actually generated or an existing starter repo was
  preserved
- the project artifact registry identifies substantive template-derived project
  artifacts by role, such as project metadata, dependency declaration, build or
  run configuration, selected source layout, selected test layout, entry points,
  or initializer-specific artifacts discovered from the generated repository
- the discovered starter artifacts are substantive: empty marker files alone are
  insufficient unless accompanied by a template-derived project metadata,
  dependency, build, source-layout, test-layout, entrypoint, or equivalent
  project artifact
- the final artifact is not Markdown-only
- template-generated source, package, build, test, entry, and tool-configuration
  roles were not overwritten by the fixed experiment overlay
- `data/`, `output/`, `results/`, and `harness/` exist
- `README.md`, `README.zh-CN.md`, `REFERENCES.md`, and
  `REFERENCES.zh-CN.md` exist
- each harness has one semantic subfolder and an explanation file
- each test category is mapped into the generated or DeepResearch-supported
  test structure and has an explanation file
- the selected test structure is justified by the template output or by
  DeepResearch evidence when the template generated no tests
- no fixed top-level test directory exists unless the template or
