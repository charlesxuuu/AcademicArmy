# Academic Army Repo Scaffold

## Purpose

Initialize a real research-code starter repository, then add the Academic Army
experiment scaffold. The primary artifact is the generated starter repo plus
fixed experiment overlay. `README.md`, `README.zh-CN.md`, `REFERENCES.md`, and
`REFERENCES.zh-CN.md` are supporting documentation, not the scaffold itself.

This skill is scaffold-only. Do not implement the paper method, experiment
workflow, data loaders, metrics, result exporters, harness logic, test logic,
configuration parsing, or experiment runners. You may invoke an initializer,
template tool, official starter command, or template repository to generate
starter files, boilerplate source, package metadata, build/test configuration,
minimal entry files, and ecosystem conventions. Do not install project
dependencies, run generated code, run tests, run harnesses, or execute
experiments.

Interpret scaffold-only narrowly: no paper business implementation. Do not
interpret it as no starter source, no package metadata, no build config, or no
template boilerplate. Those starter files are the core scaffold product.

If the final repository would contain only Markdown files, empty directories,
and placeholder notes, stop and report that scaffold generation failed. A
documentation-only artifact is not a completed repository scaffold.

## Required Inputs

Require a user-specified target repository path. If the path is missing, ask
for it before creating files.

Read only the inputs needed to scaffold the repository:

- `paper_blueprint`
- experiment plan
- coding plan
- explicit user constraints about language, framework, template, repository
  path, or existing repository adaptation

If explicit planning paths are provided, read those files. Otherwise locate the
closest conventional planning artifacts by name, then stop. Do not explore
unrelated nearby files, logs, source trees, notebooks, dependency manifests, or
old outputs merely because they are present.

Read files inside the target repository only when the user explicitly asks to
initialize or adapt an existing repository, when an initializer generated files
there that must be inspected, or when an existing scaffold file must be
preserved.

## Path And Preservation Rules

Keep every created or modified file under the target repository path. Resolve
the target path before writing and reject any path that escapes it.

Inside repository documents:

- Use repository-relative paths for files inside the generated repository.
- For planning inputs outside the repository, label them as external task
  inputs. Prefer the user-supplied workspace-relative convention, or a stable
  relative path from the repository root such as `../paper_blueprint.md` only
  when it truly resolves outside the repository. Avoid hardcoded machine
  absolute paths unless the user supplied only absolute paths and no portable
  convention exists.
- Use the same external-input path convention in README, REFERENCES, and any
  manifest.

If the target path already contains files, classify them before changing
anything:

- existing starter-repo files to preserve
- generated placeholder docs that can be refreshed safely
- generated scaffold residue that can be pruned safely
- user-authored or ambiguous content that must be preserved

Create missing scaffold files and folders. Do not overwrite non-placeholder
content. Ask before destructive replacement when authorship is unclear.
If the existing target is a previous Markdown-only or documentation-only
scaffold, do not accept it as initialized. Upgrade it by generating or merging
a real starter repository layer, while preserving any user-authored content.

Keep runtime mechanics out of generated repository documents. Do not write
about sandbox limits, shell failures, MCP failures, dependency-install
failures, or local workaround details unless the user explicitly asks for
operational notes outside the scaffold.

## Required DeepResearch

Run `academic_army_mcp_tools.deepresearch` before choosing the initializer or
template, unless the current task includes a fresh, directly relevant lookup
artifact that already compares scaffold-generation options.

DeepResearch must focus on ways to actually generate starter repository
structure for the target ecosystem:

- official initialization commands
- template tools such as Cookiecutter, Copier, Yeoman, framework CLIs, or
  ecosystem package generators
- high-quality template repositories or GitHub template repositories
- research-code templates, benchmark templates, and harness templates
- high-quality public repositories in the paper domain, used for structure
  lessons or later implementation references

Do not hardcode a tool, language, package manager, test framework, config file,
or source layout in the skill. Select at invocation time based on the planning
inputs, explicit user constraints, template quality, license clarity,
maintenance, generated output shape, and downstream implementation cost.

When no language/runtime is specified, infer a practical starter ecosystem from
the plans and DeepResearch evidence. For research systems with simulation,
metrics, trace processing, and CAGS/PyTorch/CUDA adapter boundaries, a Python
research-code starter is often plausible, but still justify the choice from the
task evidence. Leaving language/runtime undecided is a validation failure
unless adapting an existing repository that already has a clear starter
ecosystem.

Use a prompt like:

```text
Research template-first repository initialization options for an Academic Army
research-code project.

Project context:
[paper goal, field, candidate methods, experiment plan harness needs, coding
plan logical modules, explicit language/framework/template preferences, target
repository constraints]

Return scaffold-generation evidence:
- official initializers, template tools, template repositories, research-code
  templates, benchmark templates, and related high-quality repositories
- expected generated output shape for each candidate: source directory,
  package/dependency metadata, build/test config, entry files, docs, examples
- license, exact release tag, package version, commit SHA, or dated unpinned
  access snapshot
- maintenance and complexity notes
- which candidates are safe to generate from, adapt, cite only, or reject
- recommended initializer/template for this project and why
```

If multiple candidates remain plausible, compare their generated output shape
before choosing. It is acceptable to inspect documentation, run a dry generator
in a disposable location, or clone a template for static inspection. Do not
evaluate candidates by descriptions alone when generated structure is unclear.
Record the comparison at the level of generated files and directories, not only
feature descriptions.

## Template-First Scaffold Design

Use a hybrid layout:

- **Template layer:** generated by the selected initializer, template tool,
  official starter, or template repository. This layer should provide real
  starter-repo structure such as `src/`, package metadata, build/test config,
  minimal entry files, examples, or ecosystem-specific directories.
- **Experiment overlay:** fixed Academic Army directories and documentation
  required for every scaffold.

Always create or preserve these top-level overlay entries:

- `data/`: input data and future dataset assets
- `output/`: program run outputs and intermediate artifacts
- `results/`: experiment result records and paper-facing summaries
- `harness/`: all research/evaluation harnesses
- `test/`: all functional test categories
- `README.md`: English repository overview
- `README.zh-CN.md`: Chinese repository overview
- `REFERENCES.md`: English provenance and external references
- `REFERENCES.zh-CN.md`: Chinese provenance and external references

The fixed directories define top-level experiment workflow semantics only. They
do not prescribe the language ecosystem's internal source layout. Preserve the
starter repo's source directories, package metadata, dependency declarations,
test structure, build configuration, minimal entry files, and ecosystem
conventions unless they are unrelated sample-app residue or ambiguous
third-party code with unsuitable licensing.

Distinguish template starter code from paper business code:

- Starter boilerplate generated by the selected template may remain.
- Minimal template entry files may remain if they are part of normal ecosystem
  scaffolding.
- Paper-specific scheduling, CAGS integration, metrics, data loading, result
  export, harness execution, and test logic must not be implemented.

Empty marker files such as `__init__.py` or `.gitkeep` are useful, but they do
not by themselves prove starter generation. A new scaffold needs at least one
substantive ecosystem marker such as package metadata, build configuration,
framework config, generated source/package layout, or initializer-specific
project file.

If a template generates directories whose names overlap the fixed overlay
semantics, keep the fixed top-level Academic Army convention and explain the
relationship in the README. Do not let template directories replace
`data/`, `output/`, `results/`, `harness/`, or `test/`.

## Scaffold Manifest

Before writing final docs, build a compact scaffold manifest. It should be the
single source of truth for generated documentation and validation:

- target repository root
- external planning inputs and path convention
- inferred language/runtime and rationale
- selected initializer/template/tool/repository
- generation command or generation method
- template source URL, license, version/package version/commit/access snapshot
- generated starter files retained
- generated files removed or adjusted, with scaffold-level reason
- candidate templates considered and rejected reasons
- fixed overlay directories
- harness names, purposes, metrics, inputs, and artifacts
- test category names, fixtures, pass/fail meaning, and protected areas
- current scaffold tree
- static validation checklist and next implementation handoff

Do not include sandbox notes, tool failure logs, dependency-install problems,
or local workaround details in the manifest or generated repo docs.
Keep docs compact: the manifest may hold the detailed tree and comparison
notes; README and REFERENCES should summarize without repeating every
placeholder description.

## Harness And Test Placeholders

Derive harness categories from the experiment plan and coding plan. Create one
semantic subfolder under `harness/` for each harness. Use readable names such
as `candidate-method-selection`, `full-system-deadline-qoe`, or
`coupled-stress-robustness`, not abstract labels such as `c1`, `c2`, or `h3`.

Each harness subfolder must contain a short explanation file, normally
`README.md`, describing:

- harness purpose
- associated experiment goal or paper claim
- future entrypoint that should be implemented later
- expected inputs
- expected metrics
- expected output artifacts
- implementation placeholder and ownership boundary

Derive test categories from the coding plan's testing structure. Create one
semantic subfolder under `test/` for each category, such as `data-loading`,
`metric-computation`, `result-export`, or `cli-smoke`.

Each test subfolder must contain a short explanation file describing:

- functional behavior to validate
- future fixtures or toy inputs
- expected outputs or exceptions
- pass/fail meaning
- harness or implementation area protected by the tests
- implementation placeholder and ownership boundary

Harness/test notes reserve structure only. They must not contain working
harness logic, test code, fixture data, or claims that validation is already
implemented.

## README Contract

Create both `README.md` and `README.zh-CN.md`.

Both READMEs must describe the actual generated scaffold and cover:

- project purpose and external planning inputs
- inferred language/runtime and why it was selected
- selected initializer/template, generation method, and template source
- starter-repo structure generated by the template layer
- fixed experiment directories and their intended use
- reserved harness and test locations
- what later implementation skills should fill in
- scaffold-only boundary

The English and Chinese READMEs need not be literal translations, but they must
agree on the template source, generated structure, input path convention,
harness list, test list, and handoff point.

Do not claim that the paper method, experiment pipeline, harnesses, tests,
metrics, loaders, exporters, or runners already work.

## REFERENCES Contract

Create both `REFERENCES.md` and `REFERENCES.zh-CN.md`.

They must record DeepResearch provenance and the final template-generation
decision. Each source entry should use explicit fields:

- `name`
- `url`
- `license`
- `version_or_commit`: release tag, package version, commit SHA, documentation
  version, or dated unpinned access snapshot
- `access_date`
- `used_for`: final template source, generation tool, structure pattern,
  harness organization, test organization, dependency candidate, rejected
  candidate, or later implementation reference
- `selection_reason`
- `reuse_decision`: generated-from, retained, adjusted, consulted,
  cited-only, rejected, or future implementation reference
- `copied_or_generated_files`: exact retained/generated files or `none`

Prefer exact pins. If a source cannot be pinned, record it as a dated unpinned
snapshot and state why. Do not use vague phrases such as "latest
documentation", "current documentation", branch visibility, or commit counts
as substitutes for exact pins or dated snapshots.

For the selected template or initializer, REFERENCES must state:

- generation command or method used
- license and version/commit/source snapshot
- which generated starter files were retained
- which generated files were removed or adjusted
- why this option was selected over rejected candidates

If DeepResearch finds useful external implementation code, cite it as a future
implementation reference only. Do not copy or port implementation code during
this scaffold stage.

Use `consulted` for sources used only for ideas or vocabulary. Use
`generated-from`, `retained`, or `adjusted` only when the source actually
produced files in the repository or a generated file was scaffold-level
modified.

## Workflow

1. Resolve the target repository path and confirm it is the only write scope.
2. Read the paper blueprint, experiment plan, coding plan, and explicit user
   constraints only.
3. Extract scaffold requirements: ecosystem signals, expected implementation
   direction, experiment types, harness categories, test categories, input data
   expectations, and output/result artifact families.
4. Run DeepResearch for official initializers, template tools, template
   repositories, research-code templates, benchmark templates, related repos,
   and generated output shapes.
5. Infer and record the language/runtime. Do not leave it undecided when
   creating a new scaffold.
6. Compare candidate generated structures and choose an initializer/template.
7. Generate the base starter repository inside the target path. If the target
   already contains generated documentation-only scaffold residue, generate in
   a disposable location and merge the starter files into the target rather
   than overwriting ambiguous content.
8. Preserve template-generated starter structure and remove only unrelated
   sample-app residue, unsuitable third-party code, or files that conflict with
   the scaffold boundary.
9. Overlay fixed directories: `data/`, `output/`, `results/`, `harness/`, and
   `test/`.
10. Add semantic harness/test placeholder folders and explanation files.
11. Create `README.md`, `README.zh-CN.md`, `REFERENCES.md`, and
   `REFERENCES.zh-CN.md` from the manifest.
12. Run static scaffold validation. If starter generation did not occur or no
   ecosystem-specific starter markers exist, fail the task instead of
   delivering a Markdown-only repository.

## Static Validation

Perform static checks only. Do not install dependencies, lint, format, type
check, run generated code, run tests, run harnesses, run scripts, or execute
experiments.

Validation must confirm:

- every created or modified path is inside the target repository
- a starter repo was actually generated or an existing starter repo was
  preserved
- at least one ecosystem-specific marker exists, appropriate to the selected
  ecosystem, such as `pyproject.toml`, `package.json`, `Cargo.toml`,
  `CMakeLists.txt`, `src/`, generated package/module files, build config, test
  config, or a documented initializer-specific marker
- the starter marker is substantive: empty marker files or `.gitkeep` files
  alone are insufficient unless accompanied by package metadata, build config,
  framework config, or another generated ecosystem file
- the final artifact is not Markdown-only
- template-generated source/package/build/test/entry structure was not
  overwritten by the fixed experiment overlay
- `data/`, `output/`, `results/`, `harness/`, and `test/` exist
- `README.md`, `README.zh-CN.md`, `REFERENCES.md`, and
  `REFERENCES.zh-CN.md` exist
- each harness has one semantic subfolder and an explanation file
- each test category has one semantic subfolder and an explanation file
- README and REFERENCES agree with the selected template source, generation
  method, retained/generated files, fixed overlay directories, and actual tree
- planning inputs outside the repository are labeled as external task inputs
  and use a consistent portable path convention
- generated docs do not describe placeholders as implemented functionality
- REFERENCES records selected and rejected template candidates with licenses,
  versions/commits/snapshots, reuse decisions, and copied/generated files

Treat these as validation failures:

- no starter repo generation occurred for a new scaffold
- a previous Markdown-only scaffold is preserved without adding a starter
  repository layer
- the final repository has only Markdown files and directories
- language/runtime is left undecided for a new scaffold
- README says no template files, code, package metadata, config, or starter
  files were generated
- final decision is "manually assembled" when the target was a new scaffold
- absolute local machine paths are used in docs despite a portable external
  input convention being available
- REFERENCES marks a source as `adapted` or `retained` when it was only
  consulted for organizational ideas
- `copied_or_generated_files` claims files from a source when those files were
  not actually generated, copied, retained, or adjusted
- active paper business logic, experiment workflow, harness execution, metric
  computation, loader/exporter code, or real tests are implemented

## Final Response

Summarize:

- target repository path
- selected language/runtime and generation method
- template or initializer source, version/commit, license, and why selected
- starter repo files/directories retained or adjusted
- fixed experiment directories overlaid
- harness and test placeholders reserved
- static validation performed, including starter-marker and non-Markdown checks
- preservation decisions or skipped overwrites
- next implementation handoff point

Keep the response focused on the starter scaffold and experiment overlay. Do
not present dependency installation, runtime execution, test results, harness
results, or experiment results unless the user explicitly requested separate
operational work outside this skill.
