这个skill属于一套基于Codex的autoresearch工具链，任务是根据`coding plan`和当前代码库完成代码实现、修改、测试和代码审阅。
这个skill的核心风格是少抽象、少状态、少转换、强命名、强边界、强顺序一致性。
写代码时应优先做最小必要改动；不要defensive，不要过度函数化，不要为了“架构感”添加中间层、包装函数、转换函数或临时类型。
能内联就内联，能简化就简化，能删除helper就删除helper；代码应短、直、少层级，让数据流一眼可见。

skill只沉淀写代码和审阅代码时的代码质量偏好、命名规则、边界规则、prompt规则和验证规则。
只有直接影响“写出来的代码是否符合作者风格”的规则才适合留在这个skill里。
工具权限、沙盒限制、命令fallback、文件系统故障、MCP故障等运行环境问题属于外层agent/tooling规范，不应写进skill，也不应出现在代码审阅报告中。
如果某条规则放进任何skill里都适用，例如工具不可用时如何fallback、如何绕过沙盒读文件、如何处理临时故障，它就不是代码风格化skill的专属内容。
skill不应因为某次运行遇到工具问题，就把临时操作经验固化成长期代码风格规则。
skill输出或代码修改报告中应聚焦代码修改、验证结果和必要说明，不输出工具失败、环境限制、沙盒问题、文件读取策略或MCP失败处理等与代码风格无关的内容。

作者风格必须来自用户提供的代码样例、作者修改意见、review记录、已有项目上下文或明确风格要求。
当用户提供了明确风格要求时，应优先视为风格契约，不要在后续生成中反复质疑、重新验证或用无关代码覆盖这些要求。
如果需要分析作者风格，应优先关注作者提出的修改意见，因为修改意见比原始代码更能体现作者真正想要的风格。
如果不同样例之间存在冲突，应优先参考更近的用户修改意见、更明确的风格要求，以及与当前任务更相似的代码场景。
不要凭空发明作者偏好，也不要把某个项目的偶然实现写成通用规则。
不要写死某个语言、框架、文件结构、仓库布局或具体代码符号；这个skill应保留语言无关、任务无关的通用风格规律。

这个skill应采用最小任务上下文策略。
只读取和当前代码风格任务直接相关的输入，例如用户指定的代码样例、目标修改文件、作者修改记录、当前任务说明和必要上下文。
不应主动探索当前目录下的无关文件、旧计划、日志、草稿、临时输出、历史版本或其他skill的中间产物来猜测作者风格。
当前目录中的其他文件即使看起来可能有帮助，也不应默认读入；只有当用户明确指定，或当前任务文件明确依赖某个文件时，才把它作为相关上下文处理。
如果风格证据不足，应基于已有证据做保守归纳，或在输出中简短说明不确定点，不要通过读取无关目录内容来制造噪声。

这个skill应描述“如何判断并复现作者风格”，而不是把某一次代码库里的具体结构、具体文件、具体命名或具体实现写死。
只有在多个修改意见中反复出现，或被作者明确强调的偏好，才应上升为通用规则。
不要把“当前项目需要这样写”升级成“所有项目都必须这样写”。
不要为了让skill看起来完整而加入过细的模板、固定字段、固定流程或固定检查表。
如果某条tips会限制未来在其他语言、框架或项目中的正常写法，应改写成更抽象的风格原则。

编写这个skill时应优先用正向语言描述期望输出，例如生成短、直接、少层级、命名精确的代码。
必要边界可以保留，但应尽量转化为目标导向的正向约束，例如“只保留有真实语义价值的抽象”比泛泛禁止抽象更适合写进skill。
反向限制只保留高风险边界，例如不把runtime workaround写进skill、不读取无关目录内容、不写死具体语言或项目结构。
skill的规则应帮助生成更好的代码，而不是让模型陷入过度防御、反复兜底、过度解释或不敢做决策的状态。

如果这个skill用于直接写代码，输出应聚焦代码修改本身和必要的简短说明，不应输出无关背景、skill内部流程或风格分析长文。
如果这个skill需要生成解释或报告，解释应说明“为什么这段代码符合作者风格”，而不是解释skill模板、内部规则、工具调用或执行环境。
输出中不要泄漏“我是根据某个skill规则这样写的”这类元信息。
不要让skill把风格分析过程误写进代码注释；注释只服务代码理解，不服务展示skill的推理过程。

用户明确指出的风格偏好应被持续记录为已确认约束，例如不要过度函数化、能内联就内联、不要复杂编号、不要写死路径、不要探索无关文件。
后续任务中，如果用户已经明确过某个风格偏好，skill应直接继承，不要再次把它当作待确认问题。
用户后续修正某条风格规则时，应以最新修正为准，并更新旧规则，避免新旧偏好同时残留。
随着用户明确的偏好越来越多，skill应越来越确定，而不是每次都重新发散分析一遍作者可能喜欢什么。

skill本身的tips应使用自然标题、语义化原则和bullet组织，不依赖复杂编号系统。
不要使用`C1/C2/C3/B1/B2/B3`这类抽象编号来描述代码风格规则。
如果需要引用某条风格偏好，应使用自然简称，例如少抽象原则、局部性原则、命名一致性原则、内容与引用分离原则。
检查清单可以使用bullet points；只有当步骤顺序真的重要时才使用局部编号。

这个skill的任务是让代码更像作者写的，而不是替代架构设计、实验规划、测试规划、论文规划或项目管理。
如果当前任务本身要求实现功能，skill应在实现功能时应用作者风格。
如果当前任务只要求改风格，skill不应顺手重构业务逻辑。
代码风格化skill可以与其他skill协作，但不要把其他skill的职责写进本skill。
skill应保持可复用：无论目标代码属于什么语言、框架、项目类型或任务场景，都能应用作者如何组织代码、命名、抽象、状态和说明的通用偏好。

实现时应先理解现有代码结构和用户给定任务，再做贴近当前代码库模式的局部修改。
如果任务只是重命名、文案调整或路径引用更新，不应顺手重构逻辑、整理无关代码或引入新抽象。
如果用户明确说“不改文件内容”，只改路径引用、import/export、命名或配置连接，不做额外整理。
技术债清理应以删除不必要结构为主，而不是再加一层适配器。

如果一段逻辑只用一次、很短、没有独立语义，优先内联在使用点附近。
只有真正复用、表达不变量、约束边界或显著提升局部可读性时，才抽函数。
不要创建“拆开又合上”的helper；如果函数只是把数据拆分后又传回同一处，或者只是把字段从一种名字转换成另一种名字，应删除并直接传递原始结构。
简单写文件逻辑可以直接`await writeFile(...)`；如果helper只是包一行写入且不承担额外语义，应删除helper。
不要为了未来可能扩展而提前引入复杂状态机；当前简单`for` loop能表达清楚时，就不要使用复杂分支或图式工作流。
条件分支只保留真正必要的业务分支，不要为了覆盖想象中的流程增加过多分支。

类型定义应靠近使用位置。
只有多个文件共同依赖的稳定公共类型才放进共享`types.ts`。
单个agent、单个模块或单个文件专用的变量类型应放在对应文件顶部。
共享基类只承载所有子类真正共同需要的不变量和工具。
可选helper、特殊case helper、只有一两个类使用的辅助方法应放回使用它的类里。
factory应尽量只负责实例化。
如果校验逻辑属于某个对象的构造不变量，应放进该对象或基类构造函数里，而不是在factory里额外包一层helper。

命名必须语义精确，并反映领域契约和数据真实含义。
优先使用领域契约中的完整名称；能写`paperBlueprintPath`就不要写含糊的`blueprintPath`，能写`codingPlanPath`就不要写泛化的`planPath`。
文件名、类名、agent key和变量名应尽量短而语义完整。
删除冗长但不增加信息量的前缀；角色文件名应收敛到`interpreter.ts`、`reviewer.ts`、`auditor.ts`、`manager.ts`这类核心角色名。
显式保留项目里已经约定的拼写和术语，即使它看起来不常规；如果用户指定了`artifactrAchiveDir`这类拼写，不要自行“纠正”。
如果变量名带`Path`，它就应该真的是路径。
如果变量内容已经是文本，就不要保留`Path`后缀。
直接内容应使用`currentTask`、`developerReport`、`harnessReport`、`review`、`audit`这类无`Path`后缀的名字。

改名时必须全链路同步。
类型、变量、prompt文本、CLI参数、配置文件、factory、index导出、pipeline调用、脚本中的名称都要一起改。
如果一个概念在prompt、类型、CLI和配置中同时出现，应把它视为同一个contract字段，保持名称一致。
不要让旧概念残留在变量名、CLI参数、prompt文案、archive目录名或报告里。
删除`round`后，相关`last round`、`round-XXX`、`max-rounds`都应同步清理。
改名完成后应搜索旧名残留。

必填输入应建模为必填。
不要给核心路径或核心契约文件设置隐藏默认值。
如果`targetPath`、`paperBlueprintPath`、`experimentPlanPath`在语义上必需，就应在类型、CLI校验和prompt里都体现为必需。
CLI参数定义顺序、destructuring顺序、必填校验顺序、options字段顺序应尽量一致，方便人工对照。
对象字段顺序应服务比较和阅读；如果两个类型或两个对象语义对应，应尽量保持字段命名和排序一致。

agent输入、pipeline局部变量、archive输出和跨轮状态必须分层清楚。
只有真正由外部传入的agent输入才放进`DevelopingAgentVariables`这类agent变量类型。
只在pipeline内部派生、保存、归档、传递的变量应留在pipeline局部。
pipeline派生路径不要伪装成通用paths对象字段。
response输出路径、archive输出路径、一次性临时artifact路径，应在使用点附近局部构造。
不要为路径集合单独创建`DevelopingPaths`这类中间类型，除非它提供了真实抽象价值。
如果只是把options解析成另一个同构对象，应直接在函数开头内联构造局部变量。
不要为了“整洁”创建`commonVariables()`这类转换函数；如果字段名可以对齐，就直接构造`agentVariables`并传递。

一次性运行中产生的内容，优先使用“内容变量 + pipeline归档”的模型。
如果某个artifact只在本次循环内产生、随后归档，不要让后续agent再通过文件路径读取它。
这类内容应在pipeline中以字符串变量传递，pipeline负责保存到archive。
跨轮或跨运行需要保留的稳定状态可以通过路径传递。
单轮内的`currentTask`、`developerReport`、`harnessReport`、`review`、`audit`这类临时内容优先用字符串传递。
避免使用不可靠的运行状态作为长期语义。
不要记录`round`这种中断重启后含义不稳定的概念；需要限制次数时用`maxIterations`，需要归档时用timestamp archive。

代码顺序应尽量反映实际执行顺序。
imports、exports、factory对象、pipeline中的agent调用、类型映射顺序应帮助读者从上到下理解流程。
pipeline控制逻辑、agent输入变量和archive保存逻辑不应混在同一个类型里。
每个变量属于哪一层，就放在哪一层。
代码应让输入从哪里来、哪些变量传给agent、哪些内容由pipeline保存、哪些状态跨轮保留都直观呈现。
优先让结构本身表达意图，而不是靠注释解释绕来绕去的数据流。
注释只保留能解释非显然决策的内容；如果代码可以通过简化变得自解释，优先简化代码而不是增加注释。

prompt文本也是代码质量的一部分。
prompt开头不要写`You are ...`式角色扮演句；直接描述任务，例如“Interpret the coding plan into one bounded implementation task.”
prompt中读取文件的说明优先写成`Read:`列表，而不是塞进一个长句。
prompt里不要出现没有上下文的裸文件名。
文件输入用`${...Path}`变量指代，直接嵌入的文本内容用自然section名指代，例如`Current task`、`Developer report`、`Contract audit`。
路径上下文应清晰且低噪声；如果agent在某个`workspacePath`下工作，传给prompt的路径应尽量转成相对该workspace的路径，避免绝对路径污染prompt。
prompt输出要求应说明“在response中输出内容，由pipeline保存”。
不要写`Output review.md only`这类容易让agent误以为要自己写文件的表达。
如果pipeline负责落盘，就不要让agent prompt同时暗示agent要写同一个artifact。
写入责任必须单一，避免agent和pipeline职责混淆。
如果用户指出某个文案会误导agent，就把文案改成直接描述真实执行责任。

代码审阅应优先检查行为正确性、边界归属、命名一致性、状态可靠性和是否存在无意义抽象。
审阅时应主动指出多余helper、无意义类型、同构转换、旧名残留、裸文件名、误导性prompt输出、pipeline-only变量泄漏到agent变量、以及可以内联的单行包装函数。
审阅不应默认要求更多抽象、更复杂分层或更全面defensive处理。
如果代码已经足够直接，审阅应避免提出“为了整洁再抽一层”的建议。
如果发现变量属于错误层级，应建议把它移回真实拥有者所在层，而不是通过新类型或适配函数绕过去。
如果发现路径变量和内容变量混用，应要求用`...Path`和内容名区分真实语义。
如果发现运行时偶然状态被写进长期模型，应要求改成稳定状态、iteration计数或timestamp archive。

修改代码后应运行项目已有检查，至少包括类型检查、格式检查和lint诊断。
如果项目没有完整检查命令，也应运行与本次修改最相关、成本合理的验证。
验证报告要短，直接列出执行过的命令和结果。
输出汇报应简洁说明改了什么、验证了什么、还有什么未验证。
不要写过多解释性废话。

最终提交前做一次style hygiene检查。
检查是否有多余helper、过度函数化、无意义共享类型、同构转换、旧名残留、命名泛化、错误`Path`后缀、pipeline-only变量泄漏到agent变量、裸文件名、误导性prompt输出、职责重复写入、顺序不一致、或者可以内联的单行包装函数。
如果这些问题存在，应优先通过删除、内联、改名、移动到使用点和对齐字段顺序解决。

**Minimal direct code原则**：生成的代码应短、直、少层级；能内联就内联，能删除helper就删除helper，能直接传递就不要转换。
**Use-site locality原则**：类型、helper和特殊逻辑尽量放在使用点附近；只有真正跨文件共享的稳定逻辑才抽到公共文件。
**Semantic naming原则**：命名必须反映领域契约和数据真实含义；不要用泛名、旧名、缩写名或错误后缀掩盖真实语义。
**Layer ownership原则**：agent输入、pipeline局部变量、archive输出、跨轮状态必须分层清楚；哪个层负责的数据就放在哪个层。
**Prompt-as-code原则**：prompt文本也是代码的一部分；它应任务导向、路径清楚、输出责任明确，不写角色扮演废话，不写会误导agent操作文件的句子。
**Order mirrors execution原则**：代码顺序尽量反映执行顺序和类型对照关系；读者从上到下应能自然理解调用链。
**No stale runtime concepts原则**：不要把中断重启后不稳定的运行概念写进长期状态；需要运行次数就用iteration，需要归档就用timestamp archive。
**Review for deletion原则**：审阅时优先发现可删除、可内联、可移动到使用点的结构，而不是默认建议新增抽象。
**Verify after change原则**：每次改完都运行项目已有check、format和lint，并简洁报告结果。
**Task-specific skill boundary原则**：这个skill只包含仿照作者代码风格写代码所需的知识；工具调用、沙盒限制、文件读取失败、运行环境fallback和其他runtime问题不进入skill。
**Evidence-bounded style modeling原则**：作者风格必须来自用户提供的代码、修改意见和明确要求；不要凭空发明风格，也不要把某个项目的偶然实现写成通用规则。
**Minimal relevant context原则**：只读取当前任务必需的代码和风格证据；不要探索当前目录下的无关内容来猜测风格。
**Language-agnostic abstraction原则**：tips只描述语言无关的风格特征，例如少抽象、强命名、局部性、顺序一致、数据流清晰；不绑定具体语言、框架、文件路径或仓库结构。
**Positive style constraints原则**：优先用正向语言定义期望风格，减少防御性限制；规则应推动代码变得短、直接、清楚，而不是让模型过度谨慎。
**No skill-process leakage原则**：输出代码和说明时，不暴露skill内部流程、模板选择、工具使用或风格推理过程；只呈现符合风格的代码和必要说明。
**User preference accumulation原则**：用户明确过的风格偏好应持续作为约束继承；后续修正应覆盖旧规则，避免重复询问或新旧规则并存。
**Natural rule organization原则**：skill规则使用自然标题、语义化原则和bullet组织，避免复杂编号和抽象交叉引用。
